# Phase 4: Drafting

Only start when the records from phases 1–3 are `accepted`. Tell the user you are starting phase 4
and repeat the short disclaimer.

## 1. Decide which documents are needed

Build a matrix from the accepted records: jurisdictions × audience × features → documents.
Use the "When is it required" section of each file in `references/doc-types/`. Typical results:

| Situation | Documents |
|---|---|
| Any website/app processing personal data of people in the EU/EEA, UK or CH | privacy-policy |
| Non-essential cookies/trackers/SDK storage | cookie-policy (or a cookie section in the privacy policy) + consent banner texts |
| Commercial website with a provider established in DE/AT (and most EU states) | imprint |
| Contracts with users (accounts, paid plans, SaaS) | terms |
| B2C distance sales in the EU/UK with a withdrawal right | withdrawal-notice (+ model form, + withdrawal function in the UI) |
| B2B SaaS where customers upload personal data | dpa |

Write the result into a decision record ("Documents to produce", typically `LDR-0004`) including
documents you decided **not** to produce and why. Ask the user to confirm.

## 2. Gather sources per document

For each document, open its checklist in `references/doc-types/<doc>.md`, collect the source IDs
for the relevant jurisdictions, and **fetch each source now** (source-policy.md). Read the
specific provisions, note pinpoints, log them in `sources-used.md`. If something fails, follow the
fallback procedure before writing a single clause that depends on it.

## 3. Draft

File: `docs/legal/documents/<doc>.<lang>.md` (e.g. `privacy-policy.en.md`, `imprint.de.md`).
Use Markdown unless the project needs another format (MDX, HTML, JSON for a CMS). Then write the
draft in Markdown first and convert it at the end.

Every document starts with this banner (translate it for other languages, keep its meaning):

```markdown
> **DRAFT – generated by an AI coding agent, not legal advice, not reviewed by a lawyer.**
> Do not publish before a qualified lawyer has reviewed it. Defense report:
> `docs/legal/defense/<doc>.md`. Version 0.1, <date>.
```

Then:

- **Traceability comments.** After each clause or section, add an HTML comment that does not
  render: `<!-- LDR-0001, LDR-0007 · EU-GDPR Art. 13(1)(a), DE-DDG § 5(1) Nr. 1 -->`.
  Clauses based on a non-bundled or non-official source get `· REPLACEMENT` or
  `· NON-OFFICIAL SOURCE`. Clauses you could not verify at all get a **visible** marker
  `[UNVERIFIED – model knowledge, check with a lawyer]` and `· UNVERIFIED` in the comment.
- **Only facts from records.** Every name, address, provider, purpose, retention period comes
  from an accepted LDR. If it is missing, write `[[TODO: …]]` and list it in the defense report.
  Never invent placeholders that look real (no "Musterstraße 1", no fake register numbers).
- **Describe reality.** The privacy and cookie policies must match the processing inventory,
  including the gaps. Never claim consent is collected if the code loads trackers before consent,
  never promise security measures or deletion that the code does not implement.
- **Plain language.** EU-GDPR Art. 12 and UK-CRA2015 s. 68 require clear, intelligible
  language. Short sentences, headings that match the checklist, no "may" or "some" where you can
  be specific (EU-EDPB-TRANSPARENCY).
- **Mandatory wording is copied, not paraphrased.** Statutory model texts (DE-EGBGB-MUSTER,
  EU-CRD Annex I, UK-CCR2013 Sch. 3, AT-FAGG Anhang I), required button labels and required
  notices (US-TX-TDPSA sensitive-data notice) are reproduced exactly, with the design notes applied.
- **No copied third-party texts.** Do not copy another company's policy or a commercial
  generator's output. Statutory texts are fine.
- **Jurisdiction sections.** For multi-jurisdiction documents, keep a common core and add clearly
  headed sections ("Information for residents of California", "Hinweise für Verbraucher in
  Österreich"). Do not mix the GDPR and UK GDPR into one undifferentiated claim.
- **Languages.** Draft the binding language first. Translations are translations: mark which
  version prevails (if the user decided, see records). Translated statutory model texts must be
  the official version in that language, not your translation.
- **Version and date.** Version `0.x` while in draft. The defense report holds the changelog.

## 4. Consistency pass

Before phase 5, check across all documents: same entity name and address everywhere; every
processor in the privacy policy appears in the inventory and vice versa; cookie list matches the
code; terms and withdrawal notice agree on periods and exceptions; links between documents work;
the imprint contact matches the privacy policy controller (or the difference is explained).

## 5. Things documents cannot fix

Collect implementation duties you found, with the source, and give them to the user as a
separate list (they are not legal text): consent banner behaviour, withdrawal function and
cancellation button in the UI, order button label, Do-Not-Sell link and Global Privacy Control
handling, account deletion, self-hosting fonts, DPAs to sign with processors, records of
processing (EU-GDPR Art. 30), registering a DMCA agent, paying the ICO fee, appointing an EU/UK/CH
representative.
